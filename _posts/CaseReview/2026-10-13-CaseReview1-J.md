## 一、 背景

1. **ビジネスの変遷に伴う既存ロジックの破綻**: 旧実装の引当在庫計算ロジックはリリース当初こそ正常に機能していたものの、業務の運用変化に伴い、一部のテーブルの運用形態やカラムの定義・セマンティクスが当初の設計から乖離していった。その結果、計算結果に歪みが生じ、現在の業務要件を満たせない状態に陥っていた。
    
2. **Team Leader からの提案**: 今回のバグ改修を契機として、全体的により良い書き方ができないか検討してみるよう提案を受けた。


## 二、 既存実装の課題

### 1. データベースエンジンレイヤーにおける物理的ボトルネック

- **可観測性の欠如**: 動的SQLの条件分岐によってクエリの骨格が固定されず、安定したクエリハッシュ（Query Hash）が得られないため、本番環境で実行性能メトリクスを集約・追跡することが極めて困難であった。
    
- **実行計画キャッシュの肥大化（Plan Cache Bloat）**: 動的SQLによってクエリの骨格（述語パターン）が固定されず、条件の組み合わせごとに再利用性の低い実行計画が量産され、メモリ領域を浪費していた。
    
- **実行計画ドリフトの潜在リスク（Plan Drift）**: 検索条件の動的な組み合わせごとに、オプティマイザの基数見積もり（Cardinality Estimation）に乖離が生じやすく、実行計画の予期せぬ反転（Plan Flipping）やパフォーマンスの急激な悪化を引き起こすリスクを孕んでいた。
    
- **物理I/Oスパイクの懸念**: 将来的なデータ量の増加に伴い、制御不能な実行計画がバッファキャッシュを突き抜け、突発的な物理ディスク読み取りの急増（Buffer Cache Thrashing）を引き起こす潜在リスクが存在していた。
    

### 2. ソフトウェアエンジニアリングおよび保守性における課題

- **ドメインルールとワークアラウンドの混濁**: 後続の保守担当者にとって、クエリ内のコードが「正規のビジネスルール」なのか、それとも「過去の不具合対応や暫定回避策（Workaround）」なのかを判別できない状態になっていた。
    
- **ビジネスロジックの構造的分断**: 単一の巨大SQLという構文上の制約により、ひとつの業務ルールが `JOIN ... ON` の結合条件、動的な `WHERE` 句、さらにはネストされた `SELECT ... CASE WHEN` 式へと強制的に分断されていた。この断片化が、保守時のワーキングメモリを著しく圧迫していた。
    
- **コードレビューの死角とテスト容易性の低下**: 動的SQL内の文字列連結やエスケープ処理は目視での静的解析が難しく、些細なタイポを見落としやすかった。また、ビジネスルールごとの明確な分岐単体テストを実施することも困難であった。
    

## 三、 コアアーキテクチャの思想と設計原則

1. **業務制約の境界の明文化**: 実装に着手する前にまずすべての業務ルールを洗い出し、システムが満たすべき必須の業務制約を漏れなく明確に整理する。
    
2. **手続き的条件分岐から集合演算（JOIN）への転換**: リレーショナルデータベース（RDBMS）は、行ごとの手続き的な条件分岐判定よりも集合演算（ジョイン / JOIN）の処理に特化している。手続き的な WHERE 判定は、可能な限りルールテーブル（Rule Table）やドライビングテーブル（Driving Table）に対する結合へと書き換える。
    
3. **責務境界の分離（Separation of Logical and Physical）**:
    
	- 開発者は業務フロー全体のコンテキストを把握しているため、処理パイプライン全体のデータフロー、およびマテリアライゼーション（中間実体化 / Materialization）の境界設計を主導する。
    
	- データベースオプティマイザ（Optimizer）は業務全体の文脈を感知できないため、その探索空間をあらかじめ局所的なサブセットへ厳格に制約し、インデックスシークやスキャン（Index Seek / Scan）といった物理アクセスパスの最適化に専念させる。
        
4. **リクエストコンテキストの統一（Unified Request Context / `@ctx`）**:
    
    - 外部から渡される離散的なパラメータを単一の真実のソース（SSOT: Single Source of Truth）へと集約し、パラメータの変動からコアエンジンを隔離すると同時に、デバッグや境界値検証における唯一の検証ポイントを提供する。
        
5. **段階的パイプライン処理（3層のテーブル変数）**:
    
    - 各フェーズの中間結果の保持にテーブル変数（`@TableVariable`）を採用する。後続フェーズから直接参照できるようにするとともに、明確なデバッグ観測点（インスペクションポイント）を提供する：
        
        - **Layer 1: Line-item Filtering（明細絞り込み）**: 統一された `@ctx` に基づき、有効な計算対象明細をフィルタリング。
            
        - **Layer 2: Master Attribute Enrichment（マスタ属性補完）**: ルールテーブルと結合し、明細に対してマスタ情報および関連ディメンション（Dimension）を付与。
            
        - **Layer 3: Cascading Stock Calculations（段階的在庫計算）**: 現在庫（On-hand）、引当在庫（Reserved）、有効在庫（Available）を連動して段階的に算出。
            

## 四、 アーキテクチャの演繹プロセスと数理モデルとの整合

1. **アーキテクチャ演繹のメンタルモデル**:
    
    - 試行錯誤的な積み上げではなく、すべての業務制約を脳内で同時に展開する。多次元制約の交差と暗黙的な枝刈り（Implicit Pruning）を通じて、最適なリレーショナルトポロジー（Relational Topology）へと直接収束させたため、アーキテクチャ設計自体は極めて短時間で完了した。
        
2. 数学的視点における事後的な整合性（事後調査・理論マッピングの参考）:

	本リファクタリングの完了後にコードの構造を振り返り、改めて調査を行ったところ、実装した各機構が数理ロジックや抽象代数の各領域と構造的に合致していることが確認できた。個人的には「世界の基礎は数学であり、優れた設計は必然的に何らかの数学的原理に整合する」と考えている（※以下は理論的マッピングの参考として整理。筆者自身も現在学習中である）：

- データ定義層: 集合論の外延的定義（展開テーブルによるビジネスルールの事前実体化）
- 全体アーキテクチャ層: 圏論における射の合成（@ctx を引き渡す純粋関数的な3層パイプラインの結合）
- 関係・属性層: 集合の直積と一階述語論理（インライン行コンストラクタによる局所タプル化と述語制限 $\sigma$）
- 制御フロー調停層: 順序論と束論における極大元・極小元（半順序集合による優先度フォールバックと理由抽出）
        

## 五、 システム実行フレームワーク

1. **ルール＆マトリクス層（Rule & Matrix Layer）**: 静的な業務制約および多次元マッピング定義。
    
2. **統一リクエストコンテキスト（`@ctx`）**: 標準化されたパラメータパースおよびフィルタリング基準。
    
3. **3層計算パイプライン（Three-tier Runtime Pipeline）**:
    
    - Layer 1: 明細の抽出、述語プッシュダウン、カーディナリティの削減。
        
    - Layer 2: マスタデータのディメンション補完。
        
    - Layer 3: 在庫階層ごとの段階的配分および引当計算。
        
4. **最終集約（Final Aggregation）**: コンテキストと倉庫属性に基づき、最終的な決済在庫およびドメインフィールドを出力。
    
5. **後続フィルタ（Post-calculation Filter）**: 計算結果から導出された派生フラグに対する評価（例：「出荷不可」理由の判定）。
    

## 六、 具体的実装パターンと可観測性

### 1. ルール＆マトリクスモデル（Rule & Matrix Model）

- **倉庫合算ルールの「設定・フラット展開」メカニズム**:
    
    - **Table 1（保守用ルール定義テーブル）**: 人間が保守する高位の業務定義を保持する。倉庫Tag（例: Tag 1 = 主倉庫属性A, Tag 2 = 主倉庫属性B, Tag 3 = ベンダー倉庫属性A, Tag 4 = ベンダー倉庫属性B）や資材適合ルールなどを管理。
        
    - **Table 2（自動展開マッピングテーブル）**: マスタ更新時に、Table 1 の多次元ルールを全網羅したフラットな参照テーブルへと自動展開する。手続き的な分岐判定を、単純かつ静的な等価結合へと平坦化する。人間は Table 1 のみを保守し、Table 2 はシステムが自動生成する。
        
    - **実務上のメリット**:
        
        - `IF/ELSE` 分岐を排除し、決定論的な等価結合（Equi-join）によって一括処理が可能。
            
        - テスト・監査の容易化: 計算時はまず**全パターンを展開したフラット計算**を先行して行い、各分岐の中間数値を明確に観測できるようにする。その後、Tag ごとに集約し、`@ctx` と組み合わせて最終在庫を算出する。
            
- **配送マトリクスの多次元区間マッチング**:
    
    - 業務的な意図が不明瞭なマジックフラグ（`-1 / 0 / 1`）の採用を避け、連続した明示的区間（`[min, max]`）による物理範囲定義へ移行。
        
    - **実務上のメリット**:
        
        - `@ctx` の値が包含される区間判定による配送ルールのマッチング。
            
        - ドライビングテーブル（Driving Table）との区間結合（Range Join）により、適合資材を効率的に絞り込む。
            

### 2. 計算レイヤー（Calculation Layer）

- **`APPLY` 演算子による優先度制御**:
    
    - `CROSS APPLY` / `OUTER APPLY` を用いて優先度付きルールセットから動的に最優先の資材属性を抽出する。カーソルやループ処理を排除し、高い拡張性を担保。
        
    - 同様のメカニズム（Mechanism）は後続処理でも再利用され、例えば「出荷不可となった具体的理由」の判定・抽出にも適用されている。
        

### 3. デバッグと堅牢性の担保（Debugging & Observability）

- **`SET STATISTICS IO` と AI を活用した即時プロファイリング**:
    
    - 初版実装完了後、`SET STATISTICS IO` を有効化して各処理ブロックの論理読み取り数（Logical Reads）を監視。
        
    - プロファイリングツールの存在は把握していたものの、メトリクスの詳細な物理挙動までは熟知していなかったため、その場でAIを活用して論理読み取りの背後にある物理メカニズムを学習・特定。
        
    - 把握した指標に基づき、負荷の異常なオペレータに対して微調整（ドライビング順序の是正や不要なフルスキャンの排除）を実施し、論理読み取り数を圧縮して将来的なスケールリスクを未然に防止。
        
- **大域的 `TRY...CATCH` と実行時SQLコンテキストの補足**:
    
    - 実行ロジック全体を構造化された `TRY...CATCH` ブロックでカプセル化。
        
    - 実行時エラー発生の際、その時点のSQL実行コンテキストを補足し、エラーメッセージとともに対象のSQLコードブロックを直接出力。
        
    - SQL Server 標準のエラー行番号が実際のエラー箇所と乖離しやすい問題を解消し、どのブロックで何が発生したのかを即座に特定可能にした。
        

## 七、 チーム方針とのすり合わせとトレードオフ

### 1. テーブルエイリアスの命名規則（Aliasing）

- **トレードオフ**:
    
    - **旧来の1文字エイリアス（`a-z`）**: 旧実装は十数個のテーブルを単一スコープで結合するモノリシッククエリであったため、名前衝突を防ぐ目的で `a, b, c...z` といった機械的エイリアスに依存していた（肥大化したスコープに対する対症療法）。
        
    - **自己文書化されたスコープ**: 段階的パイプライン化により各フェーズのスコープが極めて短く、参照エンティティも少数となったため、完全なテーブル名（または業務ドメイン名）をそのまま使用する方が可読性が高く、「`d` が何を指すか」を遡る必要がなくなる。
        
- **採用結果**:
    
    - リファクタリング時点では命名規則に関するチーム全体の合意形成が過渡期であったため、チームの既存の慣習を尊重し、従来の1文字エイリアス運用を維持した。
        

### 2. ソート処理の実行場所（Sort）

- **トレードオフ**:
    
    - 当初はSQL内部で一時テーブル（`#TempTable`）を用いて決定論的なソートを行う構成を検討。
        
    - チームから一時テーブルは「キャッシュに残り続ける懸念がある」として使用を避ける方針が提示された。その説明に疑問は残ったものの、当時の自分には低レイヤーの挙動を検証・判断できるだけの知識が不足していたため、チームの判断に従った。
        
- **採用結果**:
    
    - SQL内での一時テーブルによるソート案を取り下げ、チームの提案に従い、ソート処理はアプリケーション層側へ移譲した。
    
### 3. 中間データの格納媒体（Storage）

- **トレードオフ**:
    
    - チーム規約としてテーブル変数（`@TableVariable`）の採用が義務付けられていた。
        
    - テーブル変数と一時テーブルの内部挙動（統計情報の保持機構など）を調査・比較したが、今回のワークロードにおいて一時テーブルが圧倒的に優位であると断定できる決定打は見当たらなかった。
        
- **採用結果**:
    
    - チームの規約を厳格に遵守し、各パイプラインの中間データ保持にはテーブル変数を一貫して採用した。
        

## 八、 技術詳細：`CASE WHEN` を排除する実装パラダイム（`APPLY` + `VALUES` の3パターン）

多分岐判定や動的プロパティ取得に伴う深い `CASE WHEN` のネストを完全に排除するため、`CROSS APPLY` / `OUTER APPLY` と行コンストラクタ（`VALUES`）を組み合わせ、手続き型ロジックを集合操作へと変換した。実運用においては、以下の3つのデータフロー再構築パターンに分類される：

### 1. 構造層：インライン行コンストラクタによる局所タプル化（Inline Tupling / Column-to-Row Inversion）

- **メカニズムと実装**:
    
    - ワイドテーブルの単一行に含まれる横方向の複数カラムを、縦方向の `(MatchTag, Val)` タプル行へとオンザフライで分解・展開する。
        
    - 実行時の動的なカラム選択判定を、生成された仮想行セットに対する静的な等価結合述語（`WHERE c.MatchTag = @ctx.RequiredTag`）へと変換する。
        
- **パターンコード**:
    

SQL

```
CROSS APPLY (
    SELECT c.Val
    FROM (
        VALUES 
            ('TAG_A', d.ColA),
            ('TAG_B', d.ColB)
    ) c(MatchTag, Val)
    WHERE c.MatchTag = @ctx.RequiredTag
) resolved
```

- 数学原理・理論モデルにおける対応:
  - 集合論：デカルト積上の元（タプル）構成と外延的定義（Cartesian Product & Extensional Definition）:
    $D_{\text{Tag}} \times D_{\text{Val}}$ という直積集合の空間に対し、行コンストラクタ（`VALUES`）を用いて要素を外延的に列挙することで、局所的な二項関係（仮想タプル集合）を直接インスタンス化している。
  - 一階述語論理：制限算子への写像（First-Order Predicate Restriction $\sigma$）:
    手続き型の条件分岐（`CASE WHEN`）を排除し、構成された局所タプル集合に対して一階述語の制限算子（$\sigma_{c.\text{MatchTag} = @\text{ctx}.\text{RequiredTag}}$）を適用することで、純粋な関係代数演算へと還元している。
  - 代数系：関係代数の閉包性（Relational Closure Property）:
    属性の動的選択を `APPLY` 局所の関係演算として完結させ、入力・演算・出力がすべて同一の代数系（関係・タプル集合）の内部で閉じる構造を維持している。

### 2. 状態・制御層：複数ソースのフォールバックと優先度調停（Priority Fallback Pipeline）

- **メカニズムと実装**:
    
    - **Layer 2 での事前タグ付与**: 資材属性や配送区分に基づき、前段パイプラインであらかじめ計算に必要な業務Tagを導出。
        
    - **Layer 3 での調停**: `APPLY (VALUES ...)` を用いて複数のデータソースを優先度付き候補セット `(Priority, SourceVal)` として構成し、最上位を抽出することで決定木を平坦化：
        
        - **優先度 1**: 明細テーブルに明示的に指定されている倉庫。
            
        - **優先度 2**: Layer 2 のルールから推導されたデフォルト倉庫。
            
- **適用シナリオ**:
    
    - 対象の引当在庫が今回の計算対象範囲に含まれるかの判定。
        
    - 「明示指定があればそれを優先し、無ければルール適用」という多層ネスト判定を平坦な行セット選択に置き換え、集約クエリ内のネストされた `IF...ELSE` を排除。
        

### 3. ドメイン層：出荷不可理由のマッピングと抽出（State-to-Reason Projection）

- **メカニズムと実装**:
    
    - Layer 3 で評価された各ブールフラグを受け取り、`APPLY (VALUES ...)` を用いて優先度付きのエラー理由行セットへ投影する：
        
- **パターンコード**:
    

SQL

```
OUTER APPLY (
    SELECT TOP 1 Reason
    FROM (
        VALUES 
            (IsStockShort,  '在庫不足', 1),
            (IsInvalidAttr, '資材要件不一致', 2)
    ) r(IsHit, Reason, Priority)
    WHERE r.IsHit = 1
    ORDER BY r.Priority
) unship_reason
```

- **適用シナリオ**:
    
    - 明細が「出荷不可」と判定された際、優先度順に基づいて主要因となるメッセージを1件抽出する。
        
    - 業務判定ロジックと表示テキストを完全に疎結合化し、文言の修正や優先順位の変更が発生しても、上流の在庫計算パイプライン自体に手を加える必要をなくす。
